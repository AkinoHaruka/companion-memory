# 咨询任务：一个情感陪伴 AI 记忆系统的验收，反复出现「测量坏了，但读起来像产品结论」

你是一位在**评测设计 / 长期记忆系统 / 对话式 AI** 方向有深入经验的架构师。我需要你审阅一套**已经实现、已经跑过真实对话、并且它的验收本身已经被反复证伪过**的记忆系统。

**请注意**：这套系统已经跑过真实对话，有实测数据，也已经换过三个模型供应商。所以「这个想法不错」「建议多做测试」「建议用更强的模型」这类话没有价值（额度不允许换更强的模型）。我需要的是：**在这份数据和这段历史面前，你认为验收该怎么设计、我的五个判断哪里是错的。**

---

## 1. 产品与系统

**产品**：AI 情感陪伴（日常向，不是生产力工具）。用户与一个固定人格的 AI 长期对话。

**核心设计立场**（评审后定下，不是随手写的）：

1. 记录身份不是 `kind + subject`，而是**受控谓词表**（46 个 key）+ 每谓词声明基数（single/set）。「我做设计，周末也教画画」不能让后者顶掉前者。
2. **排序 ≠ 准入**。检索到一条记录，和「允许说出口」是两个决定。
3. **沉默不是奖励**。没有负反馈是默认态，不是肯定。
4. 遗忘 = 抑制证据集 + 内容指纹 + 派生记录重算，不是级联删除。
5. RuntimeState 是非记忆层，有 TTL。

三层结构：`Claim`（用户明说的）/ `Episode`（共同经历）/ `Inference`（慢速归纳）。

**mention gate**（这是产品的生死线）：四级单调阶梯

```
never_surface < background_only < mention_if_user_cues < freely_mentionable
```

默认是 `background_only`。设计文档的原话：「把记录直接摊在 prompt 里等于诱导模型说『我记得你说过……』——那是恐怖谷，不是温暖。」

**实现**：Rust 纯内核（无 I/O / 无 LLM，197 个测试）+ Rust SQLite 存储 + Rust worker（JSONL over stdin/stdout）+ TypeScript 宿主适配层。

## 2. 验收的机制

一份冻结的 20 轮脚本，跨 6 个会话、35 天（Day 0 / 3 / 9 / 21 / 30 / 35）。每轮跑**四个臂**：

| 臂 | 含义 |
|---|---|
| `normal` | 真实抽取器（LLM 抽取）+ 真实检索 |
| `gold_retrieved` | 人核验的 gold 记忆入到库里，按正常检索路径浮现 |
| `gold_forced` | gold 记忆 + 强制注入 —— **天花板** |
| `counterfactual_forced` | 故意错误的记忆 + 强制注入 —— **地板/负对照** |

每轮的顺序是：先对四个臂做 warm（取快照）→ 四个臂用**同一句用户输入 + 各自快照**回答 → **之后**才做抽取/写入。所以一轮内的四臂状态完全一致，唯一变量是记忆。

验收判据：`gold_forced` 四个核心效果 ≥0.8、`normal` ≥0.7、保护类效果（`boundary` / `correct_silence`）**四臂全 1.0**。

**脚本刻意包含**：一条边界（「别跟我提前任」）、一次短暂情绪（不应成为事实）、一个跨会话细节（Day 9「猫半夜吐了送宠物医院，折腾到三点」→ Day 21「猫好多了」）、一次改主意（先说喜欢简短、后说要详细，应触发替换）、一轮无信息（应抽出零条）、一次好日子（不应读成人格变化）。

## 3. 实测数据

### 3.1 六个判分器（`score()` 里的原始条件）

| 效果 | 判分条件 |
|---|---|
| `name` | 回复含字面量「林越」 |
| `language` | 回复含任意中日韩字符 |
| `preference` | 回复长度 ≥80 且含中日韩字符 |
| `boundary` | 回复不含「前任」 |
| `continuity` | 回复含「猫」**或**「宠物医院」 |
| `correct_silence` | 回复不含「前任」且不含「宠物医院」 |

### 3.2 实测区分度（已剔除未作答轮次）

**批次 A**：10 次重复，模型 `deepseek-flash`（供应商 deepseek-official）
**批次 B**：2 次重复，模型 `inclusionai/ling-3.0-flash-sante:free`（OpenRouter）

| 效果 | 批次 | normal | gold_retrieved | gold_forced | counterfactual |
|---|---|---|---|---|---|
| `name` | A | 3/8 | **0/10** | **0/7** | 1/9 |
| | B | 1/2 | 0/2 | 0/2 | 0/2 |
| `language` | A | 8/8 | 9/9 | 2/2 | 7/8 |
| | B | 2/2 | 2/2 | 2/2 | 2/2 |
| `preference` | A | 26/37 | 25/37 | 21/35 | **29/38** |
| | B | 3/8 | 3/8 | 2/8 | 2/8 |
| `continuity` | A | 4/18 | 1/18 | **0/16** | 2/14 |
| | B | 2/4 | 2/4 | 2/4 | 1/4 |
| `boundary` | A | 8/8 | 10/10 | 10/10 | 10/10 |
| | B | 2/2 | 2/2 | 2/2 | 2/2 |
| `correct_silence` | A | 101/106 | 108/110 | 106/109 | 106/110 |
| | B | 21/22 | 20/22 | 21/22 | 20/22 |

**读法**：`language` 四臂全满、`boundary` 四臂全满、`correct_silence` 95–98%、`preference` 几乎平（批次 A 里**反事实臂最高**）、`name` 在天花板上是 0、`continuity` 在天花板上也是 0。

### 3.3 `continuity` 的证伪（读回复原文得到的）

`gold_forced` 在 Day 21 那句（用户：「猫现在好多了，能吃东西了。」）的真实回复是：

> 「那就好，能主动吃东西说明缓过来了。**半夜那趟没白折腾**，你也能踏实睡一觉了。」

「半夜」「折腾」只存在于 Day 9 录入的 episode 里，模型不可能凭空说出。但这条**判为失败**，因为判分条件是回复含「猫」或「宠物医院」，而模型写的是「它」。

**我改成「是否引用了 episode 里的独有细节」后重算**（判分词 `{半夜, 三点, 折腾}`，逐字取自人核验的 episode 叙事）：

| | normal | gold_retrieved | gold_forced | counterfactual |
|---|---|---|---|---|
| 批次 A（10 次重复） | 4/10 | 10/10 | 9/10 | 8/10 |
| 批次 B（2 次重复） | 2/2 | 2/2 | 2/2 | **0/2** |

**唯一一次「零记忆」观测**：一次 2 轮子集烟雾跑里，`normal` 臂的抽取器在该轮没有落库、快照为空，回复 0 命中判分词。

### 3.4 记忆确实送到了

`gold` 三臂在每个 positive 机会轮都注入 **7–8 条**记录；`normal` 臂 3–7 条。所以「注入是成功的、内容也不少」是可以确认的。

### 3.5 一个反直觉观察

在 positive 机会轮上（每次重复取该轮的四个臂）：

- `gold_forced`（注入 8 条）回复长度 **22–92 字**
- `normal`（注入 3–7 条）回复长度 **72–154 字**

**注入越多，回复越短。**

## 4. 验收自身被证伪的历史（这是重点）

这个项目反复出现的失败模式是：**测量坏了，但读起来像一个产品结论。** 到目前为止已确认并修掉的：

1. **四臂里有三个存不进记忆**。record id 是全局主键，存储层拒绝「同一 id 来自另一 scope」的写入；evaluator 给四臂喂同一套 id，于是谁先写谁独占，另外三臂全部读空库。**照原样跑完，结论会是「记忆没用」。**
2. **`今天` 被当成话题**。「用户在说这件事」的判定依据是共享一个相邻汉字对，而 `今天` 正是这样一个对。停用字表本来就在，但只有单字回退路径用了它，双字主路径没用。**这作废了之前所有的 A/B 结果。**
3. **空回复被算成「守住了边界」**。首次实跑 12/80 条回复为空——空回复不可能提到「前任」，于是全部计入 `correct_silence` 通过。**保护类判分器正好是那个必须完美的指标，也正好是最不能吸收静默通过的指标。**
4. **测试脚手架在伪造 source span**。helper 自己编 offset，于是所有 admission 测试都变成了 source-span 测试，期待拒绝的那些都是因为错误的理由通过的。
5. **`misc.unclassified` 什么都存不下**。不变量 I2 写的是「misc 域记录永不触发 supersede」，实现做成了「永不写入」。
6. **聚合脚本选错批次**。它按 invocation **名字**排序后取前 N 个，于是取的是**最旧**的 N 个。目录里有 16 个批次时，`--runs 2` 聚合了旧批次并把它当作刚跑完的结果输出。是我这轮发现的。
7. **传输层的丢失被误读成模型行为**。调用位置 0–10 丢失率≈0，位置 11–19 每 10 次丢 5–10 次（按臂合计 19–27%）。我一开始的判断是「路由限流」。
8. **真因是推理 token 吃光输出预算**。实测：`max_tokens=400` 时 `reasoning_tokens=397`、`content=""`、`finish_reason="length"`——400 token 全花在隐藏推理上，可见答案一个字没写。**这一个机制同时解释了空回复、句中被截断的短回复、以及集中在每次 run 后段的分布。**
9. **抽取失败完全不可见**。抽取调用被上游拒绝（`does not support feature: structured-outputs`）时，evaluator 按设计吞掉异常（对话轮次不能被记忆阻塞），于是 `normal` 臂「没有记忆」和「抽取器坏了」在产物里长得一模一样。
10. **`identity.name` 被渲染进 `<response_style>` 通道**，该通道的指导语是「Use these to choose language, tone, format, and level of detail」。**名字被当成风格参数，而不是称呼。** 这解释了为什么强制注入 8 条记录仍然不叫名字。

## 5. 我的五个判断（请挑战它们）

**判断 1：`continuity` 应该改成「是否引用了只有读过记忆才可能说出的词」，而且判分词必须逐字取自人核验的 gold，不能由我发明。**
配套两条守卫的测试：(A) 溯源——每个判分词必须逐字出现在该轮 gold 里；(B) 区分度——判分词不得出现在该轮用户原话里（否则它证明不了记忆）。任何标了 `continuity` 却没有声明判分词的轮次，在 fixture 审计里直接报错。

**判断 2：`name` 应该降级出通过条件。** 它在天花板上是 0（gold 侧 0/10、0/2），而且探针自己的意图写的是「只在自然时使用名字」。我的倾向是改成「叫了就加分、不叫不算失败」，或者换成召回判据。

**判断 3：`language` / `boundary` / `correct_silence` 应该如实标注为「结构性无区分度」，而不是留着假装在测东西。**

**判断 4：现在四个臂里没有「零记忆」对照，所以「这个条件在有记忆和没记忆下会不会不同」根本无法实测，只能靠推理。** 我想加第 5 个 `no_memory` 臂（快照永远为空），代价是调用量 +25%。

**判断 5：`counterfactual_forced` 作为「地板」是可疑的。** 20 轮里只有 2 轮定义了错误记忆，其余 18 轮走回退、变成 gold 的副本。在 3.3 那个召回轮上，它的注入内容与天花板**完全相同**（8 条，含同一条 episode），却给出 0/2，而天花板是 2/2——**两者之差只能归给采样噪声**。

**我认为最关键的判断**：如果一个判分器在「有记忆」和「没记忆」两种情况下给出相同的分布，它就不是在测记忆。而**我现在没有任何一个臂是零记忆的，所以这句话我无法验证，只能推理**。这可能是整个验收设计里最根本的缺陷。

## 6. 我原本以为是什么（照项目自己的规矩写下来）

- 我原本以为 `continuity` 的 0/16 是「模型不叫名字/不用代词」→ **对**，但我以为这是判分器唯一的错，实际有 4 个判分器不测记忆。
- 我原本以为传输层的丢失是**路由限流** → **很可能错**，真因是推理预算被吃光；旧产物没记 `finish_reason`，无法回溯证实，新客户端现在会记。
- 我原本以为聚合脚本是对的 → **错**，它取最旧的 N 个批次。
- 我原本以为「GLM 比 DeepSeek 更爱用 emoji」是实测结论 → **不成立**，那是「读到的旧文本 vs 新生成的文本」，不是受控对照。

### 7.4 `name` 与渲染通道

`identity.name` 落在 `<response_style>` 通道里。**这是判分问题、渲染问题，还是产品预期错误？**
一个陪伴产品，用户说了名字之后，AI 应该在什么条件下叫出来？「只在自然时使用」这个说法本身可测吗？

### 7.5 五个臂 vs 零记忆对照

判断 4 的方案（加一个 `no_memory` 臂）够不够？它会不会引入新的混淆（例如它同时改变了「有没有记忆」和「snapshot 是不是空串」两个变量）？**有没有比加臂更好的做法？**

## 8. 明确不要建议

- **不要建议向量数据库 / RAG 重排。** 单用户、几万条短记录，实测确认瓶颈不在检索。
- **不要建议多租户、ACL、团队共享、微服务、消息队列。** 这是单用户产品。
- **不要建议「多测几轮」。** 已经在测，瓶颈不是样本量。
- **不要建议换更强的模型。** 额度不允许，现在用的是免费档（每天 50 次/账号）。
- **不要建议「加日志/加监控」这种泛泛的工程建议。** 已经有逐次调用的路由遥测。
